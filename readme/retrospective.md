## 배운 점 : 상태 처리와 보이는 모습 처리 나누기

`.on`, `.off`, `.done`처럼 클래스명을 바꿔 넣으면서 화면을 바꾸는 방식은 이해했지만, **어디까지를 JS가 관리하고 어디부터 CSS에 맡겨야 하는지** 경계를 정하는 게 어려웠습니다. 그래서 요소의 상태를 종류별로 나눠서 분석하고, 각각을 어떻게 처리할지 정리했습니다.

### 1. 상태를 네 가지로 나누기

| 종류 | 예시 | 어디에 두나 | 저장 여부 |
|---|---|---|---|
| **데이터 상태** : 할 일 자체의 성질 | 완료 여부 `done`, 핀 고정 시각 `pinnedAt` | `todo.items` 배열의 객체 | localStorage에 저장 |
| **화면 모드 상태** : 지금 화면을 어떻게 보고 있나 | 정렬 기준 `sortBy`, 보기 필터 `filter` | `todo` 객체의 속성 | 저장 (새로고침해도 유지) |
| **작업 중 상태** : 사용자가 하고 있는 일 | 수정 중인 할 일 `editingUid` | `todo` 객체의 속성 | 저장 안 함 |
| **일시적 효과** : 잠깐 보였다 사라짐 | 카드 강조 `is-flash`, 핀 상자 흔들림 `is-shake` | DOM 클래스만 | 저장 안 함 |

이렇게 나누고 나니 "이 값을 저장해야 하나?", "새로고침하면 남아 있어야 하나?"라는 질문으로 어디에 둘지 쉽게 정할 수 있었습니다.

### 2. JS는 "무엇인지"만, CSS는 "어떻게 보이는지"를

JS에서 `style.opacity = .4`, `style.textDecoration = ...`처럼 모양을 직접 바꾸지 않고, **상태만 속성으로 표시**하고 모양은 CSS가 그 속성을 보고 결정하도록 나눴습니다.

```js
// JS : 상태만 표시
card.dataset.done = done;               // data-done="true"
btn.setAttribute("aria-pressed", done); // aria-pressed="true"
```

```css
/* CSS : 상태에 따른 모양 */
.todo-card[data-done="true"] { --card-bg: ...; --card-fg: ...; }
.todo-card[data-done="true"] .strike { background-size: 100% 4px; }
```

이렇게 하면 디자인을 바꿀 때 JS를 건드릴 필요가 없고, 반대로 기능을 바꿀 때 CSS를 건드릴 필요가 없습니다.

### 3. 어떤 방식으로 표시할지 고르는 기준

| 표시 방식 | 언제 쓰나 | 이 프로젝트에서 |
|---|---|---|
| `data-*` 속성 | 값이 둘 이상이거나 true/false인 **데이터 상태** | `data-done`, `data-pinned`, `data-empty` |
| `aria-pressed` | 눌림/안 눌림이 있는 **토글 버튼** (스크린리더도 읽음) | 완료 체크, 핀, 정렬, 필터 버튼 |
| `hidden` 속성 | 보이기/숨기기만 필요할 때 | 수정 취소 버튼, 수정 중 안내 문구 |
| 클래스 (`is-*`) | 데이터와 상관없는 **화면 효과** | `is-editing`, `is-flash`, `is-shake` |

처음에는 `.on`/`.off` 두 클래스를 번갈아 넣었는데, `data-done="true|false"`처럼 **속성 하나에 값을 바꿔 넣는 방식**이 상태를 하나로만 관리할 수 있어서 실수가 줄었습니다. 또 토글 버튼은 `aria-pressed`를 쓰면 CSS 선택자와 웹 접근성을 한 번에 해결할 수 있다는 것도 알게 되었습니다.

### 4. 다시 그릴지, 일부만 바꿀지

상태가 바뀌었을 때 화면 전체를 다시 그릴지(`render()`), 바뀐 요소만 고칠지도 상태 종류에 따라 나눴습니다.

- 할 일 추가·수정·삭제, 정렬·필터 변경 → 목록 구성이 바뀌므로 **전체 다시 그리기**
- 완료 체크 → 카드 하나의 속성만 바뀌므로 **해당 카드만 수정**. 전체를 다시 그리면 DOM이 새로 만들어져서 취소선이 그어지는 전환 효과가 보이지 않음
- 수정 중 표시 → 전체를 다시 그린 뒤에도 유지되도록 `render()` 끝에서 `markEditing()`을 다시 호출

## 어려웠던 점

### 1. 버그 원인 찾기

화면에 보이는 증상과 실제 원인이 서로 다른 곳에 있어서 원인을 찾는 데 시간이 걸렸습니다.

- **입력값이 다른 글자로 바뀌는 문제**: 제목에 `$&`를 넣으면 `${title}`로, `${content}`를 넣으면 내용 값으로 바뀌어 나왔습니다. 처음에는 입력 폼이나 저장 쪽 문제라고 생각했지만, localStorage에는 제대로 저장돼 있었고, 원인은 **템플릿에 값을 채워 넣는 `replaceAll`의 특수 패턴 해석과 순차 치환**에 있었습니다. 같은 자리에서 입력한 태그가 그대로 실행되는 문제(XSS)도 함께 발견했습니다. → [트러블슈팅 기록](troubleshooting.md)
- **고쳤는데 그대로인 화면**: 코드를 수정했는데 브라우저에 이전 JS·CSS가 캐시돼 남아 있어서, 수정이 안 된 것처럼 보였습니다. 새로고침만으로는 부족해서 캐시를 비우고 다시 불러온 뒤에야 확인할 수 있었습니다. 이후로는 수정 후 강력 새로고침(Cmd + Shift + R)으로 확인하는 습관을 들였습니다.
- **전환 효과가 안 보이는 문제**: 완료 체크 시 CSS `transition`을 넣었는데 효과가 보이지 않았습니다. 원인은 체크할 때마다 `innerHTML`로 목록 전체를 다시 그려서 **카드가 새 요소로 바뀌었기 때문**이었습니다. 바뀐 카드의 속성만 수정하도록 바꿔서 해결했습니다.
- **취소선까지 흐려지는 문제**: 완료한 카드를 `opacity`로 흐리게 했더니 빨간 취소선까지 같이 흐려졌습니다. `opacity`는 자식 요소 전체에 적용되기 때문이라, 카드의 배경색·글자색 변수만 흐리게 바꾸고 취소선은 선명하게 남겼습니다.

### 2. 폼 입력값 처리 : 값이 쌓이는 것과 입력창 초기화

- **값이 쌓이는(스택) 구조**: 등록할 때마다 새 할 일이 기존 목록 뒤에 쌓여야 하는데, 배열을 직접 수정(`push`, `splice`)하면 어디서 값이 바뀌었는지 추적하기 어려웠습니다. 그래서 `[...items, 새 할일]`(추가), `items.map()`(수정), `items.filter()`(삭제)처럼 **항상 새 배열을 만들어 교체**하는 방식으로 바꾸고, 바뀔 때마다 `save()` → `render()` 순서로 저장과 화면 갱신을 한 곳(`commit()`)에서 처리했습니다. 새로고침해도 쌓인 값이 유지되도록 localStorage에 JSON으로 저장하고, 저장값이 없거나 깨진 경우에는 빈 배열로 시작하게 했습니다.
- **입력창 초기화**: 등록 후 입력창이 비워지지 않거나, 수정하다가 등록을 누르면 수정 모드가 그대로 남는 문제가 있었습니다. `form.reset()`으로 입력값을 비우는 것과 함께 **수정 모드(`editingUid`), 버튼 문구, 취소 버튼, 안내 문구를 한 함수(`setEditMode`)에서 같이 되돌리도록** 묶어서 해결했습니다. 수정 중이던 할 일을 삭제하거나 Esc를 눌렀을 때도 같은 함수를 거치게 해서 상태가 어긋나지 않게 했습니다.
- **빈 값 검사**: 빈 칸으로 등록되지 않도록 `trim()`으로 공백만 입력한 경우까지 걸러내고, 비어 있는 첫 번째 칸으로 커서를 옮겨 바로 입력할 수 있게 했습니다.
